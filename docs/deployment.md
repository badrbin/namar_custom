# نشر تجربة حساب التخصيم

## النطاق والمصدر

- التطبيق: `demo`، الإصدار `0.1.0`، وFrappe متوافق `>=15.0.0,<16.0.0`.
- مستودع المصدر: `badrbin/namar_custom`، فرع مستقل `demo`؛ لا يغير الفرع ملفات `namar_test` أو فروعه.
- مجموعة البنش: `sector-realtime-20260826` / `bench-46656`.
- الموقع المصرح: `testnamar.u.frappe.cloud`.
- البنش المرجعي قبل إضافة التطبيق: `bench-46656-000027-f1uae`.

ينقل الإصدار محرك الحساب وواجهة «حساب التخصيم» فقط. لا يغيّر التصنيع أو تسجيل القيود أو الحزم، وتبقى استدعاءاتها على النظام الحالي. يتطلب التطبيق `erpnext` و`namar_test` المثبتين.

## حالة التجهيز

اجتاز الكود 30 اختبار Python و6 اختبارات JavaScript ببيانات مصطنعة. لم يُثبت التطبيق أو يُفعّل على الموقع بعد. السكربتان القديمان ما زالا المصدر العامل.

منع اتصال GitHub المستخدم هنا إنشاء مستودع جديد (`Resource not accessible by integration`)، لذلك حُفظ التطبيق في فرع مستقل داخل المستودع الموجود والمصرح. كما أعادت واجهة `press.api.github.options` في Frappe Cloud خطأ HTTP 417 من نوع ValidationError، وتضمنت الرسالة المصنفة `Error fetching installations from GitHub` و`Bad credentials`.

بعد إفادة المستخدم بإعادة الربط، ظل اكتشاف حسابات GitHub يفشل، بينما نجح طلب `press.api.bench.branch_list` للمصدر الحالي وظهر فرع `demo`. هذا يثبت وصول اتصال Frappe Cloud الموجود إلى المستودع؛ العائق المتبقي هو اكتشاف معرّف تثبيت GitHub App لإضافة مصدر التطبيق. يمكن استخدام معرّف اتصال **Frappe Cloud** الذي يقدمه مالك الحساب من رابط **Configure** في `https://github.com/settings/installations`، ثم التحقق منه عبر `press.api.github.app`. لا يُخمن المعرّف ولا يُستبدل بمعرّف اتصال Codex. لم تُغيّر صلاحيات أو مفاتيح أي اتصال، ولم يُسجّل التطبيق في Cloud بعد.

## خطوات الاستكمال

1. الحصول على معرّف اتصال Frappe Cloud من مالك الحساب أو من اكتشاف GitHub بعد إصلاح OAuth. نجح بالفعل التحقق بالقراءة من ظهور فرع `demo` في المستودع.
2. فحص `press.api.github.app` وإقرار أنه يكتشف تطبيق `demo` والتوافق مع Frappe 15.
3. إضافة التطبيق إلى `bench-46656` عبر `Release Group.add_app`، واستخدام مصدر خاص بالفرع.
4. نشر البنش عبر `press.api.bench.deploy_and_update` مع إبقاء كل App Release حالي، وإضافة إصدار Demo فقط. تبقى النسخ الاحتياطية وفحوص التصحيحات مفعّلة.
5. متابعة نجاح Build وRelease Pipeline وSite Update وانتقال الموقع إلى البنش الجديد.
6. تثبيت `demo` على الموقع عبر `Site.install_app`. يلزم نجاح Install App Job وظهور التطبيق ضمن التطبيقات المثبتة؛ لا تكفي حالة Active.
7. قراءة `demo.api.migration_status`، والتأكد من أن Demo غير مفعّل، وأن السكربتين الأصليين لم يتغيرا. قارن الحساب الجديد بالقديم على مدخلات حقيقية بالقراءة فقط.
8. بعد نجاح المقارنة، نفّذ `demo.api.activate` مرة واحدة. العملية محدودة بالموقع وبدوري System Manager وScript Manager، وتتحقق من بصمتي الكود قبل تحويل الحالة في معاملة واحدة.
9. تحقق من أن Demo مفعل، وClient Script القديم غير مفعل، وServer Script القديم معطل. اختبر الحساب باسمي API القديم والجديد، وأعد تحميل نموذج تجريبي دون حفظ مستند تشغيلي أثناء الفحص.

## التراجع

اقرأ الحالة أولًا. إذا كان التطبيق مفعّلًا والسكربتان لم تتغيرا، يعيد `demo.api.deactivate` تشغيلهما ويوقف واجهة Demo في معاملة واحدة. لا يحذف التطبيق أو الصفحات أو بيانات التصنيع. يلزم إعادة تحميل الصفحة بعد التبديل. إذا فشل تثبيت التطبيق، تبقى النسخة القديمة فعالة لأن التفعيل منفصل.

مصدر البيانات الوحيد الذي تضيفه الحزمة هو Single DocType باسم `Demo Settings`. لا تحتوي الحزمة على fixtures تستبدل تعريفات أو بيانات الأعمال الموجودة.
